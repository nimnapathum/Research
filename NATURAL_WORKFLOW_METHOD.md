# Revised methodology: natural coding with measured security judgments

**Decision, 13 October 2026.** This is the proposed protocol for the next *human feasibility pilot*. It replaces the eight forced reveal/keep/rate checkpoints as the main coding procedure. The existing portal and exported ZIP still implement the older checkpoint procedure and **must not be used as if they implement this revision**. A separate mechanics rehearsal may still test that software, but its results cannot validate natural coding behavior. Reconcile this change with the institution-approved protocol before recruiting under it.

## 1. Research claim and unavoidable tradeoff

The study asks whether assigned acceleration or exploration encouragement changes how early-career developers work with a coding agent, judge the security of their work, verify agent contributions, and leave SQL injection or path traversal in final code. Each person works on both projects, one per condition, with project and order balanced. The assigned condition is the comparison; observed interaction mode is coded independently and can change during a task.

There is no way to guarantee that every participant naturally receives an insecure agent-generated change **and** leave the agent interaction unconstrained. We therefore choose natural interaction for the main study. We will report how many actual agent outputs contained target weaknesses, how many were seen or incorporated, and what remained in final code. We will not call absent exposure a successful rejection, or infer a low retention rate from zero opportunities. If the pilot produces too few insecure agent outputs, the main study cannot make a precise claim about *retention of agent-introduced vulnerabilities*; it can still assess final-code security and verification. A separate controlled review experiment is the honest option for guaranteed secure/insecure exposure.

This choice follows the distinction between Barke et al.'s observed acceleration/exploration episodes in real programming work and studies such as Khalid et al. that deliberately present security-varying code choices. The latter supports a controlled judgment test, but it does not make a forced review gate natural. Mozannar et al. motivate observing verification after code has been accepted or incorporated, not stopping measurement at the first acceptance action. See [references](#8-source-backed-rationale).

## 2. Participant experience: start to finish

1. Obtain consent and approved screen/agent/interview recording. Ask background and experience questions that do not teach the two attack mechanisms immediately before coding. Give everyone the same neutral Antigravity practice on an unrelated feature.
2. Give the participant the first project, its full goal and security requirements, its condition card, and the complete starter code. They may read all files and documentation, ask the agent anything, prompt in their own words, let it edit, reject or replace edits, test, use scanners, or work manually. **No researcher-controlled reveal, no prohibition on editing, and no request to stop at a feature boundary.** The facilitator does not give security hints.
3. Record screen and agent transcript. Collect feasible hook/editor events and frequent, nonblocking repository snapshots or diffs. These are evidence of what happened, not a live classification of the participant's mind. If capture fails, log the gap; do not interrupt coding merely to restore a metric unless consent or data security requires it.
4. When the participant says the first project is finished or the time limit arrives, freeze the final repository. Before any test result or researcher feedback is shown, ask the participant for a 0–100% estimate that **this exact final snapshot** satisfies each named security requirement, plus a brief reason. Also ask whether they would submit it as it stands, which parts they believe the agent materially shaped, and whether they relied on the agent for the security judgment. Record final snapshot hash and rating timestamp. The confidence score alone is not a measure of trust in the agent.
5. Give a short break and a fresh second project under the other condition. Repeat the same free-working procedure. Counterbalance project and condition order. Do not show security feedback from task one before task two.
6. After both tasks, replay a small selection of participant-specific agent/code moments without disclosing the oracle. Ask what they were trying to do, whether they understood the change, when they decided it was good enough to keep working with, and what they checked. Ask whether the condition wording matched their actual approach. Debrief only after ratings and interview.

The participant's task sheet presents feature **deliverables**, not ordered pauses. The current [same-day rehearsal kit](study-system/pilot/NATURAL_REHEARSAL_TODAY.md) uses two per project: one SQL feature and one file-access feature. The participant chooses implementation order. Both projects need matched workload and time allowance; project and order remain balanced across people. Any expansion back to four features requires a new timing pilot and a frozen task version.

## 3. What is measured without a forced checkpoint

| Question | Operational evidence | Limit |
| --- | --- | --- |
| RQ1: security confidence alignment | Per task and weakness class, final-snapshot 0–100% confidence before feedback; independent target-security adjudication of the same final snapshot. Report confidence on secure and vulnerable outcomes separately; Brier score is possible but is accuracy, not pure calibration. | Final-state judgment is not confidence in an earlier agent proposal. If almost all final features have one security status, discrimination cannot be estimated well. |
| RQ2: final vulnerabilities | Normal functionality tests, target attack tests, blinded human review, and final code for all assigned SQL/path requirements. Report functional/secure, functional/vulnerable, missing feature, and unassessable. Separately count confirmed agent-origin insecure changes that were actually visible and whether their weakness survived. | Final vulnerability is not automatically caused by the agent; provenance must be traced. Natural exposure counts can differ between conditions. |
| RQ3: verification | Time-stamped screen/transcript/code sequence around each *observed* agent change: before its first integration, after first integration, repairs, tests, and final status. Code security-specific checks separately from generic reading/tests. | No explicit keep click. First integration is a behavioral proxy; ambiguous cases are `unclear`, with interview evidence kept separate. Checks and repair are associated, not randomized causes. |
| RQ4: class difference | The same measures split by SQL injection and path traversal. | With 30 people and potentially few insecure agent outputs, this is exploratory and may be descriptive only. |
| Mode | Segment the video/transcript into known-next-step, option-seeking, mixed, or unclear episodes; use participant replay to interpret ambiguous episodes. Compare with assignment as a manipulation check. | Pointer speed, elapsed time, prompt length, and number of clicks do not define a cognitive mode. |

**RQ wording for supervisor review before the main study.** The existing RQ1 can still be answered for final-code confidence, but its interpretation changes from exact agent proposal judgment to confidence in a whole submitted feature. RQ2 already asks about final code and can remain. RQ3's phrase “known exposed vulnerabilities” presumes controlled exposure that the free task cannot guarantee. A compatible wording is: “How do security verification behaviors before and after observed integration of agent-generated changes differ between conditions, and how are those behaviors associated with target vulnerabilities in the final code?” RQ4 remains exploratory. Keep the researcher's original wording in [RQ.md](RQ.md) until this change is approved; do not claim the revised procedure answers the old exposure-specific RQ3 without that amendment or a separate controlled probe.

**Natural retention event rule.** An agent-origin change becomes *provisionally integrated* when its effect first appears in the working files and the participant moves on to another action while leaving it in place. Save the earliest reliable timestamp and code hash. If the agent writes directly into files, integration can happen before the participant has read the change; code that as `agent-applied`, then separately code first participant inspection or use. Record rejection, overwrite, repair, and final survival as distinct later events. A direct file write is **not** evidence of human trust or conscious acceptance. Two coders should test this rule on pilot recordings and mark uncertainty rather than manufacture a decision.

**Agent-origin rule.** Link a change to an agent message/tool action and a code diff or video frame. Classify `agent-origin confirmed`, `mixed`, `participant-origin`, or `unknown`. An insecure starter example is not an agent-introduced flaw. An agent's inaccurate statement about a file is recorded as advice/factual error and possible priming, not as proof that the code contained the displayed snippet. Preserve the prompt/reply, actual file snapshot, and timing separately.

## 4. Security assessment and analysis

Build an ordinary functional test and a targeted negative/attack test for each assigned feature. For SQL, test whether crafted topic/name input changes query structure or broadens results. For path access, test traversal, encoded variants and permitted-root containment with harmless fixture files. Two reviewers inspect the final code and relevant data flow without seeing condition, confidence or interview; adjudicate disagreement. A scanner may flag candidates, but it is not the sole oracle. Report functionality separately so deleting a feature does not count as a secure success.

Use participant-paired condition summaries, with project/order shown. The **primary pilot outcome is feasibility**, not a significance test: can people complete both tasks naturally, do agent changes and security judgments occur, are files/transcripts/video aligned, and does the encouragement yield distinct observed episodes? Before main recruitment, freeze one primary quantitative contrast, its denominator, missing-data rule, and a sensitivity/precision table for 30 completed participants. If enough final secure and vulnerable cases occur, a prespecified paired final-snapshot Brier contrast can be considered. If they do not, use confidence and final security as separate descriptive outcomes; do not retrofit a calibration claim from a near-constant label. Estimate agent-origin vulnerable-change retention only among *confirmed visible* vulnerable changes, with counts and uncertainty, and never treat those events as 30 independent participants.

## 5. Optional controlled review study, kept separate

If guaranteed secure and vulnerable judgments are essential, run an **additional, clearly labeled review probe after both coding tasks**. Show prevalidated secure and vulnerable patches in an isolated copy, allow inspection and testing, and ask security confidence about each exact patch. Do not import those probe patches into the free-coding final submissions. Balance class/status/order and record whether patches were genuinely agent-generated or researcher-constructed. Analyze the probe as *performance in a controlled review task*. It cannot estimate unprompted agent acceptance or before/after checking in natural coding, and its condition association is weak if the probe is performed after both condition episodes. A separate randomized review experiment would be needed for a causal condition effect on controlled-patch calibration.

The existing eight-checkpoint portal is a prototype of this **controlled** type, not the natural coding protocol. Its frozen decision rating, constructed candidates, and export fields are useful for mechanics and for a future separate review experiment. They must not be merged with natural-task events under one denominator.

## 6. Pilot pass/fail decisions before any main study

- Run one researcher-only end-to-end rehearsal on the exact Antigravity version and each intended OS route. Verify consented video, readable agent transcript, file snapshots, timestamps, final-code upload, and access controls. The present ZIP/client require a review gate and therefore need redesign before this rehearsal can represent the new protocol.
- Run 2–3 wording interviews and 4–6 consented feasibility sessions. Record how often participants ask the agent to make a change before the old reveal point, whether they complete both tasks, how many confirmed agent-origin changes and target vulnerabilities occur, and whether final-confidence wording is understood.
- Check condition manipulation with independently coded episodes and post-task explanation. If both conditions look alike, revise the cards/tasks and re-pilot or describe only the assigned-wording effect.
- Check the coverage of secure and vulnerable **final** outcomes and confirmed insecure agent outputs. If sparse, narrow RQ1/RQ2 claims or add the separate controlled review study before main recruitment; do not seed hidden flaws into the natural stream while claiming spontaneous generation.
- Confirm the revised procedure, recording and data handling against the institution-approved ethics materials. An approval for the old protocol does not automatically cover this changed participant flow.

## 7. Software and document migration needed

1. In the portal, present one complete project brief and condition card per task; remove mandatory checkpoint progression, Show proposed change, and keep/reject gates from the **natural-task route**. Keep those routes only for a separately labeled controlled review probe.
2. In the participant ZIP, remove the no-edit-before-reveal instruction from the natural-task instructions. Replace `study/client.mjs` patch application with consented event/snapshot upload and finalization. The participant must be able to edit from the start. Do not silently modify an active participant package midway through a session.
3. Collect final-snapshot hashes and per-class confidence **after coding, before feedback**, and keep those responses separate from checkpoint-proposal confidence.
4. Update exports and dashboards to distinguish `natural_task`, `review_probe`, `agent_applied`, `human_inspected`, `first_integration`, `final_status`, and unknown provenance. Update the analysis scripts; current `opportunities.csv` and Brier/retention summaries implement the old gate.
5. Revise task sheets, facilitator script, consent/information sheet, interview guide, codebook, runbook and readiness audit together. Freeze one version before inviting participants; archive the prior version for reproducibility.

## 8. Source-backed rationale

- [Barke et al., *Grounded Copilot*](https://arxiv.org/abs/2206.15000) observed acceleration and exploration in programmers' interactions with a code-generating assistant. These are contextual episodes, so the present task framing is a manipulation to validate, not a direct measurement of a mind state.
- [Khalid et al., *(Don't) Trust, but (Don't) Verify*](https://arxiv.org/abs/2609.21020) studied developers evaluating security-varying AI code choices and final edits. It supports a controlled review probe, but it does not validate calling a forced gate natural agent use.
- [Mozannar et al., *Reading Between the Lines*](https://doi.org/10.1145/3613904.3641936) argue that acceptance alone misses verification and editing after acceptance. This motivates time-ordered event coding through final submission.
- [Perry et al., *Do Users Write More Insecure Code with AI Assistants?*](https://arxiv.org/abs/2211.03622) motivate measuring both security beliefs and assessed code security, without assuming either will move in a particular direction here.

The free-task protocol, integration event rule, final-snapshot confidence form and hybrid option are **this study's proposed adaptations**. The cited papers do not validate them without a feasibility pilot.
