# Data inventory and figure plan

**Design status:** This inventory and its plots describe the current controlled-checkpoint export. The proposed [natural-coding pilot](../../NATURAL_WORKFLOW_METHOD.md) needs a new export and different denominators; do not use these checkpoint figures as if they describe natural coding.

**Status: 11 October 2026; protocol and proposed outputs, no participant results.** This is the single entry point for what the study records and what it can show. Details live in [the measure definitions](../../MEASURES_AND_EVALUATION.md), [pilot inventory](../../study-system/pilot/MEASUREMENT_INVENTORY.md), [coding codebook](../../study-system/instruments/CODING_CODEBOOK.md), and [analysis export guide](../../study-system/analysis/README.md). “Available” below means the software can record or export the field; it does not mean a human session has been captured or the measure has been validated on Antigravity.

## 1. What the study can compare

```text
Participant background and baseline skill ──┬──> observed interaction and security checks
                                             ├──> confidence and first decision
                                             └──> final code security

Randomly allocated encouragement condition ──> observed interaction mode
                  │                            ├──> checks before/after first decision
                  └────────────────────────────└──> confidence and final code outcome

Project, task order, weakness class, candidate version and actual exposure
must be shown or accounted for when interpreting any comparison.
```

The **assigned condition** is the primary within-person comparison. **Observed mode** is an episode-level interpretation of what a participant was trying to do; it is not randomized and cannot be inferred from the task card, clicks or pointer speed. Security verification may be a pathway between condition and outcome, but a check–outcome association is not proof of a causal check effect. Provisional keeping is itself a participant choice, so analyses limited to kept changes have a selected denominator. This separation follows the acceleration/exploration distinction observed by [Barke et al.](https://arxiv.org/abs/2206.15000) and the need to study later verification highlighted by [Mozannar et al.](https://arxiv.org/abs/2210.14306).

The study does **not** currently collect eye gaze, global keystroke contents, all IDE editor events, a validated psychological workload scale, continuous code snapshots, or guaranteed complete agent prompt/reply data from an extension. The VS Code companion extension source is not a verified standalone Antigravity instrument. Prompt/reply, manual IDE actions and meaningful exposure depend on the exact-host video/transcript rehearsal. The current export's `eligible_exposure` is derived from a recorded `exposed_at` client event; **video-confirmed meaningful visibility is a required analyst check and is not yet a separate machine-readable field**. Treat this as a pilot and export gap, not as already solved.

**Additional pilot descriptors, if their sources prove complete:** exposure-to-first-decision time (already exported for both keep and reject), agent-wait time separated from human review, number/type/length of prompts and reprompts, distinct options considered, file or diff visits, ordinary/attack/scanner runs with inspected result, first post-keep check and edit time, edit/rewrite size, and final proposal survival. Most of these require video/transcript coding or validated editor telemetry; the present hook alone does not supply reliable human-action counts. Report explicit missingness instead of filling absent events with zero. Do not turn a fast decision, long prompt, or many cursor moves into a cognitive-mode or trust score. The detailed candidate definitions are in the [pilot inventory](../../study-system/pilot/MEASUREMENT_INVENTORY.md).

**Where the records live:** the password portal's PostgreSQL database holds accounts, task rows and questionnaires; the checkpoint service's private SQLite store holds allocation, reviews, events and snapshot references; consented video/interview and the official agent transcript are separately retained evidence. The blinded review package produces reviewer CSVs, mode/check/path coding CSVs and a private mapping. The current analysis export writes `opportunities.csv`, `task_summary.csv`, `skipped_checkpoints.csv`, `forms.csv`, `capture_coverage.csv`, optional `pointer_windows_exploratory.csv`, and `summary.json`. Keep raw evidence and analyst judgments separate, then create publication figures only from a frozen, de-identified analysis copy.

## 3. Variables to derive and denominators

| RQ | Primary/important variables | Correct unit and denominator | Interpretive limit |
| --- | --- | --- | --- |
| RQ1 | `p = security_probability_pct / 100`; `y = 1` if blinded exact proposal is target-secure, otherwise `0`; Brier contribution `(p-y)^2`; secure-item and vulnerable-item mean confidence; their separation | Exposed, video-verified, adjudicated proposal snapshots with a confidence response; paired participant task means for condition contrast | Brier is probability accuracy, combining calibration and discrimination. Four items/task cannot yield stable person-level calibration curves. |
| RQ2 | Exposed vulnerable status; first keep/reject; detected target; intentional repair; final target status and functionality; extra vulnerabilities | **All exposed vulnerable** items for the full flow and functional-secure success. Target-retention rate uses only assessable final features, with missing cases shown separately. | A rejected candidate can be replaced with vulnerable code; a deleted feature is not functional security success. |
| RQ3 | Any S1–S5 check, code and time in each phase; first check after keep; attack-test/scanner result inspected; final outcome | All coded exposed opportunities for before-decision comparison; **kept only** for after-keep; rejected branch separately. Link to final outcome among exposed vulnerable items. | Checking is a participant choice, often triggered by suspicion; association is observational. |
| RQ4 | RQ1–RQ3 quantities split by SQL injection and path traversal; condition difference within each class; difference of those differences | Same denominators as each parent RQ, then class-specific; show counts and uncertainty | Small class cells make effect modification exploratory; no LLM-wide prevalence claim. |
| Manipulation/triangulation | Assigned condition versus coded mode; task familiarity, difficulty, time pressure, prior AI/secure-coding knowledge | Episode or participant-task, stated explicitly | Self-report and observed mode are not interchangeable or validated classifier labels. |

For RQ1, show the vulnerable-item confidence directly as a safety-relevant overconfidence signal, but retain secure-item confidence so a participant is not rewarded for saying every proposal is insecure. For RQ2, report the **full exposure-to-final route** before any single percentage. For RQ3, compare a security-targeted check with an ordinary passing test; they answer different questions. [Perry et al.](https://arxiv.org/abs/2211.03622) motivates joint security-belief/outcome measurement; [Khalid et al.](https://arxiv.org/abs/2609.21020) motivates choice, evaluation and final editing; [Brier](https://doi.org/10.1175/1520-0493%281950%29078%3C0001%3AVOFEIT%3E2.0.CO%3B2) supplies the probability score.

**Core set, in recommended presentation order.** All charts should label `n participants`, `n tasks`, `n exposed proposals`, `n scored/adjudicated proposals`, and `n assessable final features` as applicable. Show counts beside percentages, participant-level points where practical, and uncertainty for condition contrasts. Use the same condition colors and SQL/path symbols throughout; accessibility should not depend on color alone. **Pilot-only diagnostics:** plot exposure-to-first-decision times as paired points or strip plots **after excluding logged breaks and separating keep/reject**; overlay selected event-aligned pointer summaries only for host feasibility. These cannot label trust or cognitive mode. Avoid a word cloud, a speed-based “mind state” graph, a raw suggestion-acceptance rate standing in for security, and a polished calibration curve from very few ratings.

## 5. Prior research: what can be reproduced versus adapted

| Prior study | What this study can deliberately reproduce or inspect | What would be an adaptation or an invalid replication claim |
| --- | --- | --- |
| [Barke et al.](https://arxiv.org/abs/2206.15000) | Code episodes where the next step was known versus options were being sought; compare with assigned encouragement and interview accounts. | Their grounded modes are **descriptions**, not a validated randomized manipulation or an IDE/mouse classifier. |
| [Perry et al.](https://arxiv.org/abs/2211.03622) | Measure both perceived security and actual code security; inspect prompt/review behavior alongside outcomes. | Their AI-versus-no-AI effect and 36% versus 7% SQL result cannot be replicated here: every participant uses an agent and tasks differ. |
| [Khalid et al.](https://arxiv.org/abs/2609.21020) | Present secure/insecure alternatives, record selection/evaluation, then inspect the edited final submission and explanations. | Their C linked-list tasks, five-choice interface and results are different; our checkpoint timing and two modes are new adaptations. |
| [Oh et al.](https://arxiv.org/abs/2312.06227) | Test response to an intentionally insecure AI suggestion and whether it persists. | A constructed checkpoint is not a poisoned live model. Label stimulus provenance accurately. |
| [Tang et al.](https://arxiv.org/abs/2405.16081) | Record validation/repair actions, IDE-visible work and interviews. | We have no eye tracker or validated standalone Antigravity editor event feed; do not imply gaze replication. |
| [Mozannar et al.](https://arxiv.org/abs/2210.14306) | Use event/video replay for retrospective episode coding and inspect work after first acceptance. | Their CUPS taxonomy and costs are distinct from Barke's modes and our security check codes. |
| [Wang et al.](https://facctconference.org/static/papers24/facct24-99.pdf) | Use episode-specific interview prompts about expectations, perceived suggestion quality and how developers validated it. | Their situated trust themes are not a numerical security-confidence scale or an outcome label. |
| [Brown et al.](https://research.google/pubs/identifying-the-factors-that-influence-trust-in-ai-code-completion/) | Record language familiarity and suggestion/context properties as possible explanations for reliance and acceptance. | Their code-completion acceptance predictors do not establish why an agent-generated security flaw was retained. |
| [Basha et al.](https://arxiv.org/abs/2510.11536) | Use timestamped IDE event streams as an engineering precedent and audit source completeness. | CodeWatcher is a VS Code system; its event coverage and AI-origin inference do not transfer automatically to standalone Antigravity. |
| [Brier](https://doi.org/10.1175/1520-0493%281950%29078%3C0001%3AVOFEIT%3E2.0.CO%3B2) | Score binary secure/insecure probability judgments with a proper score. | Brier alone is not a pure calibration measure; instrument wording and interpretation still need piloting. |

These are **method transfers or conceptual replications**, not claims that the same effect sizes will appear. The novel combination is the assigned mode encouragement, exact-snapshot security confidence, first decision, before/after security checks, and final SQL/path feature security in the same participant trace. The two CWEs were selected for serious, distinct and testable source-to-sink errors; [MITRE's 2024 Top 25](https://cwe.mitre.org/top25/archive/2024/2024_top25_list.html) does not measure LLM-specific vulnerability prevalence.

## 6. Minimum work before making these figures

1. Run a consented exact-host pilot and verify readable prompt/reply transcript, screen video, actual proposal visibility, event clocks and code snapshots. Add a **video-confirmed exposure field** to analyst data before publishing any exposed-opportunity denominator.
2. Freeze candidate provenance and the reviewed security criteria. Complete two blinded reviewer ratings and resolve differences before merging outcome labels with condition or confidence.
3. Pilot two-coder mode and verification coding. Retain raw codes and adjudication notes. Add machine-readable episode durations if the time-share figure is wanted.
4. Freeze the primary RQ1 and RQ2 contrasts, missing-data handling, bin rules and figure list before main recruitment. The current `summary.json` is descriptive; the research report must add intervals and denominators appropriate to the realized sample.
5. Keep interview excerpts, videos, names/consent and private candidate mapping in their approved restricted stores. Publish only de-identified tables/figures and task code that cannot reveal participant credentials or hidden study labels during recruitment.
