# Natural-study analysis pages

The 18 October hosted release has the original phase-specific analytics and reviewed-outcome entry. This **local working revision** adds RQ-linked displays, stricter rating-hash checks and a phase-specific feature CSV export. These additions have not been deployed. The hosted database already has migrations `004_study_phase.sql` and `005_natural_assessments.sql`; no new migration is needed for this local revision.

## As evidence arrives

1. Open **Analytics** and select **one** study phase: rehearsal, pilot, main or legacy. The page reads receipts, final security probabilities, capture health and saved forms. It plots confidence against reviewed outcome, complete participant-paired Brier scores, all-feature security states, after-task manipulation-check responses, and code change activity. Each plot shows its denominator or missing-data rule. Use **Refresh analysis** or leave the tab visible for its one-minute refresh to see newly uploaded files. A file count is a transfer status, not evidence-quality approval.
2. Open a participant code to compare their two tasks, self-reported after-task answers and the researcher-managed Google Meet link. Add or correct the link on **Evidence**; the participant does not upload video to the portal. Verify that the restricted Drive link opens and note the two task time ranges.
3. Open **Code timeline** for a task. The page shows a chart and list of all captured snapshot manifests, changed paths, a selectable previous-to-current diff, the initial-to-final diff and target source. Opened comparisons verify their source hashes. Run `audit_natural_evidence.py` separately to validate every archive and its link to the separately uploaded manifest and rating. The hosted portal never executes participant code.
4. Run functional and attack probes in a throwaway VM/container without network, credentials or personal files; `--isolated` confirms the environment but does not create it. Obtain two independent, metadata-masked code reviews. Then open the task code page and record their two coded reviewer judgments plus the resolved SQL or path outcome against the final hash. Record a short evidence or disagreement note. Corrections create a new row; the full history is in the researcher JSON export. The portal cannot establish reviewer independence by itself, so retain original sheets and probe reports.
5. After reviewed outcomes are entered, Analytics maps the evidence to RQ1–RQ4. It shows confidence separately on secure and vulnerable features, all assigned final-feature categories, paired vulnerability counts, class-specific denominators and participant-paired Brier differences. The displayed feature Brier score is `(probability_secure/100 - assessed_secure[0 or 1])²`; a task score averages SQL and path, and a participant line requires both task scores. Bootstrap intervals are withheld below three complete pairs. Empty or unassessable features are never labelled secure. Each paired estimate requires both classes to be assessable in both conditions; the Brier estimate additionally requires hash-matched ratings.
6. The code activity display reads the submitted capture and final ZIPs **without running their code**. It verifies initial and final source hashes, counts source files changed and source lines added/removed between those states, and counts intermediate snapshot intervals whose manifests list a `src/` or `lib/` change. Intermediate interval counts are manifest-based until the separate full archive audit. Activity does not establish an agent-origin change, human review, a security check or a secure outcome. The computed result is cached beside the immutable evidence, keyed by both ZIP receipt hashes and final snapshot hash; a missing or invalid ZIP yields an explicit unavailable state.
7. Download **feature analysis CSV** for exactly one phase and check its rows against raw receipts and independent review sheets. Prepare the five resolved coding tables: `coding_status.csv`, `episodes.csv`, `checks.csv`, `exposures.csv` and `session_log.csv`. On Analytics, open **Import completed coding tables** and select those files. The portal regenerates `features.csv` from the current phase, runs `natural_behavior_report.py` on the five uploaded tables, retains all inputs plus JSON/Markdown reports, and displays observed-mode shares, reviewed security checks, confirmed agent-origin exposure outcomes, check–outcome association and class-specific process counts. It refuses missing or inconsistent task coverage. If later task or assessment data changes, it marks the report stale until the tables are imported again. Keep coder originals and reconciliation records; the portal cannot infer these behavioural codes automatically. The same script can still be run locally with `--markdown-output` as a cross-check.

The live charts do **not** determine observed cognitive mode, human acceptance, verification behavior or agent-origin vulnerability exposure. Code those from the recording, agent transcript, source history and replay interview using [the natural codebook](../study-system/instruments/NATURAL_CODEBOOK.md). The feature CSV is a preparation aid, not an automatic research result. Apply [the analysis plan](../NATURAL_ANALYSIS_PLAN.md) to missingness, reviewer agreement, feature functionality, class contrasts and the final study report.

The cohort page reads small receipts and JSON files on every refresh. For each newly submitted task with both ZIPs it computes one bounded code summary, then reuses the cached result on later loads; it does not decompress every intermediate source snapshot. At most two uncached tasks are summarized concurrently. The code inspection page still opens detailed ZIP comparisons on demand and keeps at most twelve successful comparison results in a small process cache. Recording media remains in Google Drive. A real-host timing check with several completed pilots is still required for the 1 GB VM.
