# Design traceability and validity audit

**Status: 8 October 2026.** This connects the current software to [the RQs](RQ.md), [methodology](METHODOLOGY.md), [evaluation plan](MEASURES_AND_EVALUATION.md), and [source ledger](REFERENCES.md). A citation motivates a decision; it does not validate this particular task, instrument, or Antigravity implementation. The engineering dry runs used synthetic data. No human result has been observed.

## What the study can claim

The planned causal comparison is between **assigned acceleration-encouragement and exploration-encouragement task conditions**. The observed interaction mode is coded separately from prompts, video, actions and replay interview. The study asks whether security confidence about an exact supplied code state aligns with blinded security assessment, and whether exposed target weaknesses survive in the final feature. It cannot infer an internal cognitive state from the condition card, decision time, pointer speed, or a passing test.

At present, the reviewed patches are **researcher-constructed prototypes** and the portal permits **manual assignment entry**. The current system is suitable for software and mechanics rehearsals. A study reporting outcomes of *agent-generated* changes must collect a documented genuine-agent proposal pool or describe the stimuli honestly as constructed. A randomized-condition claim requires a locked, balanced allocation record made before participants are enrolled; the portal currently checks assignment shape and later consistency with the checkpoint system, but does not generate that record.

## Decision-to-evidence map

| Design decision and implementation | Supporting prior work | What is specific to this study and still needs validation |
| --- | --- | --- |
| Two assigned orientations, one of each per participant; code observed mode independently | [Barke et al.](https://arxiv.org/abs/2206.15000) describe acceleration as knowing the next step and exploration as seeking a way forward. [Mozannar et al.](https://doi.org/10.1145/3613904.3641936) show retrospective coding of programming activity. | Short orientation cards and two-task crossover are our manipulation. Preallocate project/condition/order, then pilot whether episodes actually differ; analyze assignment first and observed mode associationally. |
| Junior engineers and final-year CS/IT students with baseline skill/agent-use measures | [Danilova et al.](https://arxiv.org/abs/2103.04429) motivate screening programming experience; [Kaur et al.](https://www.usenix.org/conference/usenixsecurity22/presentation/kaur) motivate precise participant reporting. | This cohort is a bounded population, not a proxy for all developers or automatically new to agents. Baseline knowledge can explain missed flaws; it must be reported alongside reliance. |
| Two small JavaScript projects, both containing SQL and path checkpoints | [MITRE's 2024 CWE Top 25](https://cwe.mitre.org/top25/archive/2024/2024_top25_list.html) establishes importance of CWE-89 and CWE-22; [CodeQL SQL](https://codeql.github.com/codeql-query-help/javascript/js-sql-injection/) and [path](https://codeql.github.com/codeql-query-help/javascript/js-path-injection/) guidance inform source-to-sink checks. | Project matching, four checkpoints per task, secure/vulnerable balance and challenge level are original design choices. Test difficulty, salience, normal behavior and attack oracles before main recruitment. MITRE does not rank LLM-generated error frequency. |
| Controlled proposal revealed into the IDE; exact hash, provisional keep/reject, then free repair | [Oh et al.](https://arxiv.org/abs/2312.06227) study insecure AI suggestions in coding; [Khalid et al.](https://arxiv.org/abs/2609.21020) isolate selection/evaluation of AI code; [Tang et al.](https://arxiv.org/abs/2405.16081) observe validation and repair. | Our frozen, researcher-scheduled checkpoint is a structured review event, not a natural live-agent acceptance. The current patches are constructed. Confirm actual visibility on video, plausible provenance, absence of early edits, and whether the gate changes behavior. |
| A 0–100% security probability for that exact proposal, including rejected proposals | [Perry et al.](https://arxiv.org/abs/2211.03622) demonstrate that security belief and code security may diverge. [Brier](https://doi.org/10.1175/1520-0493%281950%29078%3C0001%3AVOFEIT%3E2.0.CO%3B2) gives a score for probability forecasts. | The wording and repeated rating are study-specific and may prime security review. Pilot comprehension/reactivity. Report confidence on secure and vulnerable items separately; Brier measures probability accuracy, not pure calibration or generic trust. |
| All exposed vulnerable opportunities remain in the denominator; final code is independently assessed | [Perry et al.](https://arxiv.org/abs/2211.03622) study security outcomes; [Khalid et al.](https://arxiv.org/abs/2609.21020) include final editing after selection. [OWASP review guidance](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Code_Review_Cheat_Sheet.html) supports manual review alongside tools. | Final secure functionality, rejection, repair, replacement, missing features and extra weaknesses are separate states. Task-specific tests and two blinded reviewers need pilot agreement; a scanner is supplementary evidence. |
| Security checks before/after first keep coded from video, transcript and code | [Tang et al.](https://arxiv.org/abs/2405.16081) observe validation/repair; [Mozannar et al.](https://doi.org/10.1145/3613904.3641936) show why work after initial acceptance matters; [Khalid et al.](https://arxiv.org/abs/2609.21020) study security evaluation. | Our S1–S5 codes and before/after boundary are original adaptations. Train two coders, distinguish generic tests from security checks, and report check–retention links as associations because suspicion and selection may confound them. |
| Antigravity hook + local client + official transcript + screen recording | [Antigravity hook documentation](https://www.antigravity.google/docs/hooks/) specifies invocation/tool events and transcript paths; [Tang et al.](https://arxiv.org/abs/2405.16081) and [Mozannar et al.](https://doi.org/10.1145/3613904.3641936) support multiple behavioral streams. | Hooks are metadata, not complete prompt/reply or participant-attention capture. ZIP/client delivery, clock alignment, transcript upload and video coding are engineering adaptations; exact-host and each-OS rehearsals remain unverified. The VS Code extension source is not an installed Antigravity desktop extension. |
| Exposure-to-first-decision and optional pointer summaries | [Mozannar et al.](https://doi.org/10.1145/3613904.3641936) motivate separating initial acceptance from later verification. [`pynput` limitations](https://pynput.readthedocs.io/en/latest/limitations.html) define technical OS limits. | Checkpoint latency includes wall-clock waiting and is not native suggestion acceptance time. Pointer motion is global while running, OS/device dependent and **exploratory**; it is not a validated mode, load or trust score. Missing Wayland/permission data are marked missing, never zero. |

## Implementation and analysis checks

| RQ | Captured now | Required human evidence before a defensible result |
| --- | --- | --- |
| RQ1 | Assignment, proposal hash, server-recorded reveal/first decision, confidence, exportable Brier contributions | Video confirmation of meaningful exposure; genuine provenance or honest constructed framing; two blinded security labels; wording pilot. |
| RQ2 | Keep/reject, frozen proposal, final snapshot, all-exposed outcome export | Independent final feature/functionality adjudication and lineage coding; missingness and extra-flaw review. |
| RQ3 | Hook events, transcript upload path, decision timestamps, video attachment route, coding sheets | Actual readable transcript/video and two-coder security-check/replay coding; agent vs human action attribution where possible. |
| RQ4 | SQL/path identifiers, balanced intended status within each task, class-specific export | Candidate salience/difficulty review and enough assessable observations for a cautious exploratory comparison. |

The [measurement inventory](study-system/pilot/MEASUREMENT_INVENTORY.md) lists optional signals and missing-data rules. The [pilot readiness audit](study-system/pilot/READINESS_AUDIT.md) is the operational gate. Passing a software dry run demonstrates data joins and recovery behavior; it does not establish manipulation validity, security-label agreement, real capture completeness, or an effect on people.

## Decisions to freeze before the main sample

1. Use the checkpoint CLI's seeded allocation (`node study-system/app/cli.mjs create P014`) before creating the matching portal account. Keep its output private, enter the exact project/condition/checkpoint orders, and audit balance by task order, project and candidate status. The portal's former fixed defaults were not randomization evidence.
2. Decide and document proposal provenance and participant disclosure. Never label constructed prototypes as unmodified agent output.
3. Reconcile final consent wording with screen, transcript, and optional global pointer capture. Rehearse each intended OS and Antigravity version; record any missing stream.
3a. Treat the downloaded `study/CAPTURE_CONFIG.json` as a live session credential: it is inside the agent-readable workspace. Before hosted participant use, replace that shared session credential with a task-scoped client credential or document and approve the precise exposure and retention risk. Never place personal or production secrets in the coding workspace.
4. Cognitive-pilot the condition cards and probability question; pilot task time, class difficulty, code salience, visibility and possible security priming.
5. Freeze the primary RQ1/RQ2 summaries, coding rules, candidate set, software versions, missing-data plan and sample-size rationale. Keep pointer and other high-dimensional telemetry exploratory unless separately validated.
