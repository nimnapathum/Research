# Screen-recording evaluation plan for the natural coding-agent study

**Proposed main-study coding instrument, 18 October 2026; pilot validation pending.** Use with [the current RQs](RQ.md), [natural codebook](study-system/instruments/NATURAL_CODEBOOK.md), [analysis plan](NATURAL_ANALYSIS_PLAN.md), agent transcript, and code snapshots. The recording shows visible actions, not thoughts, eye gaze, code provenance, or final security by itself. This rubric is an **adaptation to a file-editing agent**, not a published validated scale. The feasibility pilot tests it; freeze its main-study version afterward.

## 1. What to code and why

The unit of analysis is the **participant**, with two tasks. In each video code (a) intervals of implementation intent, (b) discrete agent/change/human-check events, and (c) each SQL and path feature. Keep timestamps, a short evidence note and uncertainty for every code. Link material edits to transcript/tool records and snapshot hashes. Do not infer that the participant saw an internal agent message merely because the transcript contains it.

| Layer | What to mark from the video and linked trace | What it answers | Research basis and adaptation |
| --- | --- | --- | --- |
| Intent episodes | Start/end of a known-next-step request, approach-seeking request, mixed purpose or unclear purpose; separately mark waiting and missing video | RQ1: did assigned conditions actually produce different observed interaction? | Barke et al. identified acceleration/exploration and quantified time in each mode. Our agent prompts, episode boundaries and two-task contrast are original adaptations. |
| Agent-change trajectory | Agent proposed/applied material target change; first visible display; human inspection; explicit endorsement if any; continuation with change; overwrite/repair; final survival | RQ2/RQ3: what happened between an agent edit and the final code? | Mozannar et al. showed that verification can occur after acceptance, and Khalid et al. traced selection, edits and final security. A free agent edit has no Copilot-style accept click; our continuation anchor is original. |
| Verification events | Actor (agent or human), purpose (security-specific, functional or generic), target class, action, output actually seen, result understood/issue identified, before/after application and continuation | RQ3 and RQ4: which security checks happened, when and for which weakness? | Barke et al. coded examination, execution, static analysis and documentation; Tang et al. recorded validation and repair with IDE/video evidence. OWASP motivates distinguishing security data-flow analysis from functionality testing. Our class-specific rules are original. |
| Exposure and final outcome | Confirmed vulnerable agent-origin target change, whether it was visible to the participant, whether they identified/repaired it, and independently adjudicated final result | RQ2/RQ3/RQ4: conditional exposure flow and final vulnerability retention | Khalid et al. connected evaluation and edits to security outcomes. Our natural-agent exposure criterion and SQL/path threat model are study-specific. Final security comes from masked code review and attack probes, **not** video rating. |

Primary sources: [Barke et al.](https://arxiv.org/html/2206.15000v3), [Mozannar et al.](https://arxiv.org/html/2210.14306v5), [Tang et al.](https://arxiv.org/html/2405.16081v1), [Khalid et al.](https://arxiv.org/html/2609.21020v1), and [OWASP Secure Code Review](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Code_Review_Cheat_Sheet.html). These sources support the component methods, not this complete rubric.

## 2. Event coding rules for one viewing pass

1. **Synchronise** video time with task ID, first prompt, transcript events and snapshot time. Record an offset and any gap. Code only observable intervals; mark `unclear` or `unavailable` rather than guessing.
2. **Make a neutral timeline** before judging mode or security: prompt, agent reply/tool action, changed file, human navigation/inspection, test or scan invocation, visible output, edit, continuation and task finish. Give every material target change a `change_id`.
3. **Code intent independently:** acceleration requires evidence the participant already specified the next implementation step before receiving the agent's approach; exploration requires evidence they used the agent to find or compare an approach. Speed, prompt length, test count and assigned card are not labels. A security question alone is a check, not necessarily exploration. Preserve mixed/unclear episodes.
4. **Code human awareness conservatively:** `agent_applied` means the file changed; `human_inspected` requires visible examination of the relevant code or diff; `explicit_endorsement` requires a statement or clear interface action; `continued_with_change` means subsequent work proceeded with it. None of these alone proves understanding or trust.
5. **Code a check as an action plus its evidence:** classify code/diff inspection, data-flow reasoning, an agent security question, ordinary test, adversarial test, scanner result, documentation or repair. Mark who initiated it and whether the participant saw the relevant output. An agent-run test with unseen output is not a human-reviewed security check. A plan to test later is not a performed test.
6. **Keep security purpose separate from activity:** opening a file or passing a normal test is not evidence that SQL injection or path escape was evaluated. For SQL, look for input-to-query flow, binding or an attack input. For path, look for input-to-file flow, canonicalisation/containment, traversal/absolute/symlink cases, or relevant documentation. Record generic review even when security purpose is unsupported.
7. **Assess final security later** from the exact final hash using two independent source reviewers and functional/attack evidence. Reviewers should not see confidence, condition or behavioural codes. Join the labels only after coding is complete.

Use the existing `episodes.csv`, `checks.csv`, `exposures.csv` and `coding_status.csv` headers in [natural templates](study-system/analysis/natural-templates/README.md). Keep raw coder sheets separately from resolved tables. The recording is the observation source; the agent transcript and snapshots establish message/code provenance.

## 3. Metrics to report (no single “trust score”)

| Metric and denominator | Output and interpretation |
| --- | --- |
| **Observed mode share:** seconds in acceleration/exploration/mixed divided by classifiable *active* episode seconds; also report unclear, waiting and missing seconds | Manipulation check and RQ1 context. Compare paired task shares; do not reassign a participant's experimental condition based on mode. Adapted from Barke's mode-time analysis. |
| **Human-reviewed security-check coverage:** number of SQL/path features with at least one participant-reviewed security-specific check divided by all assigned features; also show implemented-feature and confirmed-exposure denominators separately | RQ3/RQ4. Reports whether checking occurred, not whether it was competent or caused security. |
| **Check types and timing:** per-task/feature counts of mechanism review, agent question, adversarial test, scanner review and documentation; count before application, after application/before continuation, and after continuation | RQ3 process profile. Report agent-only tests and generic/functional checks separately. Adapted from Barke/Tang, with original agent timing anchors. |
| **Source of assurance:** features with only an agent's security claim/question answered, features with participant-inspected code or external evidence, and features with both | RQ3 reliance context. Asking the same agent to endorse its own output is observable, but is not independent verification. This comparison is our study-specific measure. |
| **Exposure-to-outcome flow:** confirmed visible agent-origin vulnerable changes → human inspected/not observed → identified/unclear → intentional repair/overwrite/no repair → vulnerable final/removed | RQ2/RQ3. Every arrow needs its own count and known denominator; zero confirmed exposures means retention is not estimable. Original linked measure for this study. |
| **Time to first human-reviewed security check after a material change:** elapsed observed seconds, with no-check cases shown explicitly | Descriptive RQ3 timing. Do not call it acceptance latency; screen gaps and agent waiting must be reported. |
| **Paired feature outcome and confidence:** 0–100 final-feature rating joined by final hash to independent secure/vulnerable result | RQ1 calibration evidence. This cannot be scored from video alone and is confidence in final code, not a direct agent-trust scale. |

For junior participants, report background familiarity, completion and perceived difficulty beside these measures. A missed flaw can reflect knowledge or task difficulty. Do not label a no-check task “high trust,” an insecure final result “blind acceptance,” or a long reading interval “deep security review” without supporting evidence.

### Optional pilot-only ordinal description

If a simple visual summary helps, code **observed security-verification specificity for each feature**: `0` no security-directed action in a complete recording; `1` security mentioned or agent asked generally, without inspected class-specific evidence; `2` class-specific mechanism *or* adversarial result inspected; `3` both mechanism and independent targeted result inspected. Use `U` for incomplete evidence. This is a **new descriptive rubric**, not a validated trust, skill or security-quality scale. Publish each underlying action and test coder agreement before deciding whether to retain the ordinal summary. Do not make it the primary outcome: a sound manual review may need no test, and a test may miss the flaw.

## 4. Worked coding example

At 02:00 the participant says, “Use the existing query function to add the filter” (`acceleration`, known step). At 03:10 the agent edits the SQL feature with string interpolation (`agent_applied`; code security must be confirmed separately). At 03:25 the participant opens the changed file (`human_inspected` only if the relevant lines are visibly examined). At 04:00 they run ordinary endpoint tests and read a pass (`functional_test`, not an SQL security check). At 04:40 they continue implementing the file feature (`continued_with_change`). At 08:00 they ask whether the SQL input could alter the query, inspect the response and replace interpolation with binding (`security_agent_question`, then possible intentional repair). A final secure SQL label requires independent review. The later security check counts **after continuation**; the earlier normal test does not. The vulnerability's final removal does not itself prove the participant detected it unless the trace supports that conclusion.

## 5. Reviewing efficiently and reproducibly

For each task, make three passes: (1) neutral timestamped event inventory; (2) intent and check coding with assignment/final outcome hidden where practical; (3) provenance and final-outcome linkage after independent review. Replay selected clips after both tasks using the [natural interview guide](study-system/instruments/NATURAL_INTERVIEW_GUIDE.md); ask intent and what result was actually seen before showing ratings or security findings. Participant recall helps interpret ambiguous intent but does not overwrite visible evidence. Mozannar et al. used immediate retrospective self-labeling; our shorter replay is an adaptation, so test recall in the pilot.

Two coders should independently code all pilot recordings. Compare **episode/event boundaries first**, then labels on agreed units; otherwise a label-agreement statistic hides disagreements about what the unit was. Save both original sheets, disagreements, reconciliation and a resolved sheet. For main data, predefine a double-coded subset across all four allocation sequences and no-check/repair cases; the current codebook proposes at least 25% as a resource choice. Report raw agreement and label prevalence, and a suitable chance-corrected coefficient for enough matched units. If units or positive cases are sparse, present disagreements and uncertainty rather than a reassuring coefficient. [Hayes and Krippendorff](https://doi.org/10.1080/19312450709336664) support reliability assessment; [Krippendorff et al.](https://doi.org/10.1007/s11135-015-0266-1) explain why segmenting continuous video is itself a reliability problem.

**Pilot success criterion:** a second coder can locate the same meaningful events, mode intent is classifiable without using security outcomes, checks can be linked to a feature and a phase, and the transcript/snapshots support exposure provenance. If not, revise the rules and recode the pilot before freezing the main-study instrument. A pilot with no insecure agent output still tests recording and coding feasibility, but cannot estimate exposure retention.
