## Valuable before the first pilot, but also testable during it

- Two reviewers should classify and compare the constructed candidates' target security, functionality and visual salience. The local oracles are engineering evidence, not independent adjudication. At minimum, do a pre-pilot plausibility review and document any obvious secure/vulnerable formatting cues.
- Run 2–3 wording interviews on the confidence question, provisional decision and condition cards. These can be the first *approved* pilot activity; they should precede the full coding sessions if practical.
- Budget approximately **two to two-and-a-half hours** per full session from the current methodology table, plus setup delays. The facilitator draft uses a 45-minute coding cap per task and a five-minute break; pilot timings must test whether eight checkpoints are feasible and whether fatigue or cross-task learning dominates.
- Check whether the one-paragraph acceleration/exploration cards create different *observed* interaction purposes. A failed mode manipulation is a pilot finding requiring revision before the main study, not a reason to relabel participants by assignment.
- Check whether the explicit SQL/path recognition questions and repeated security probability ratings prime security checking. Record this in the replay/debrief.
- Decide whether the two highly specific SQL/path recognition questions should remain before coding. They name the exact failure mechanisms under study and may train participants immediately before review. If moved, removed, or administered earlier as screening, revise `forms.json`, the approved wording if needed, and the pilot analysis plan before the first full session.
- Check that participants understand the acceleration card's “carry out a short implementation plan” instruction while the shared workflow temporarily forbids agent edits of the target feature. Confusion here can cause early edits or dilute the condition manipulation.
- The export gives the participant workspace all four task sheets at the start while the runbook asks them to open one at a time. Decide whether read-ahead is allowed and log it; if strict staged exposure matters, change the exporter and session process before piloting.

## Theoretical checks the pilot must answer

| Risk | What to inspect | Interpretation if it persists |
| --- | --- | --- |
| **The assigned cards may not produce distinct modes.** [Barke et al.](https://arxiv.org/html/2206.15000v3) observed that well-defined microtasks often support acceleration; four prescribed checkpoints could make both tasks similar. | Independently code known-next-step versus option-seeking episodes from prompt/video/interview evidence, especially before proposal reveal; compare with assigned card and ask whether the gate disrupted work. | Do not call assignment a measured cognitive state. Revise and re-pilot the task framing, or report only the effect of assigned instructions under a structured workflow. |
| **The instruments can prime security checks.** Explicit SQL/path baseline items, visible security criteria and eight confidence prompts may teach or cue the target. | Cognitive interviews, participant comments, check frequency by checkpoint position, and whether participants cite the survey as a clue. | Disclose the structured-review context, revise pre-task items before main recruitment if necessary, and avoid claiming natural unprompted agent acceptance. |
| **Junior knowledge can be mistaken for trust.** A miss may reflect failure to understand SQL or paths. | Record baseline skill, interview explanation, relevant code inspection and security-specific checks; compare knowledgeable and uncertain cases descriptively. | Do not label every missed flaw overtrust; bound conclusions to the recruited experience range. |
| **Confidence alignment is not a stable personal calibration trait.** Four secure/insecure judgments per task are sparse. | Pilot whether the 0–100% question refers to the exact frozen snapshot and whether participants understand the stated security criterion. | Report item/task-level confidence and Brier components, not individual calibration curves or a generic trust score. |
| **RQ3 checking associations and RQ4 class contrasts have limited causal/precision claims.** Checks can follow suspicion, and 30 people provide few class-specific pairs. | Confirm before/after action coding and all-exposed denominators; inspect missingness and class balance. | Treat checking versus removal as association, and SQL/path differences as exploratory with intervals. |

## Not required to start a feasibility pilot; required before the main study

- The main target is now **30 completed participants**. A sensitivity/precision table for that fixed target, frozen candidate set and analysis specification, independent reviewer/coder training and agreement, and a final protocol version are required before the main study, not before the first feasibility session. A scanner such as SonarQube or Snyk is optional supplemental evidence; it is not the target-security oracle.
- The VS Code companion extension is source only and has no installed VSIX. It is **not** a desktop Antigravity blocker if the host rehearsal proves that hooks, official transcript and video recover the needed events. It **is** unfinished if extension telemetry is promised as a required data source.
- The exported `AGENTS.md` files are neutral. There is no hidden Markdown instruction attack in the current RQ1–RQ4 protocol. Adding one would create a new manipulation and require its own disclosure, task validation and analysis plan.
