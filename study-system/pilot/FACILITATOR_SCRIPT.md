# Facilitator script — use with the approved participant materials

Use the institution-approved consent and information sheet verbatim. This script only standardizes study operation. Add its version and any deviation to the session log. The researcher knows candidate status; avoid discussing it until debrief.

## Start, about 10 minutes

1. Confirm eligibility, consent, the approved recording permissions, and the participant code. Ask them to close notifications and personal windows. Start recording only at the point allowed by consent; say the participant code and current task code aloud as a synchronization marker.
2. Say: “There are two small JavaScript projects. You may use the coding agent, tests, documentation and any normal checks. Please work as you would on the assigned objective. The task sheet states the security requirement.”
3. Give the pre-task form **before tool training**. Do not infer that a participant is an AI novice from student or junior status; record the measured experience answers.
4. Give the same agent-mode orientation and [practice exercise](PRACTICE_TASK.md) to everyone. Say: “You can ask the agent to inspect or discuss the step. Please keep the target file unchanged until the review link appears. After the first decision you can change or replace anything.”

## Each task and checkpoint

1. Read the assigned orientation and task sheet exactly as written. Say: “Please tell me when you are ready for the proposed change.” Do not urge speed, exploration, security checking, or trust beyond the assigned card.
2. At the pause, say the task/checkpoint code aloud for recording. Prepare the next assigned checkpoint. Hand over only the participant review link; keep the researcher terminal and candidate status out of video.
3. Say: “The proposal appears when you click Show proposed change. You may inspect it, ask the agent, run tests or scan it. Please give your first keep/reject answer and security estimate before editing this proposed code.” Do not recommend a specific check.
4. After submission, say: “You can now repair, replace, reject or keep the implementation. Tell me when this checkpoint is finished.” Do not interpret the provisional answer as final acceptance.
5. Record start/end and any prompt, capture, patch, recording or timing problem. If an interruption occurs, follow [recovery](SESSION_RUNBOOK.md); never supply an answer for the participant.

## Between tasks and finish

1. Snapshot the first task, give its after-task form, offer a five-minute break, and mark the second task recording segment. Use a fresh participant workspace for task two.
2. Snapshot task two, give its after-task and after-both forms. Conduct the replay interview using the existing [interview guide](../instruments/INTERVIEW_GUIDE.md), choosing moments before viewing the security labels where possible.
3. Deliver the approved debrief. Stop recording according to consent. Attach files, run audit, and write down missing streams and deviations immediately.

**Time rule for pilot:** plan up to 45 minutes coding per task, plus a break and interview. If the cap is reached, tell the participant that time is up, record which checkpoint was reached, and use `skip ... time_limit` for each remaining checkpoint. Record actual times; adjust this cap only through a documented protocol revision after pilot evidence. The pilot evaluates whether eight checkpoints and this cap are realistic. This cap is a design choice, not an effect estimate from previous research.
