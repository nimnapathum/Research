# Natural-task data coverage and safety gate

**Status, updated 18 October 2026:** The hosted natural portal has passed a synthetic two-task delivery/upload/retrieval rehearsal and serves newly generated `2026-10-18-api-contrast-v1` packages. Previously issued ZIPs remain frozen. The newer RQ-linked analytics remain local. The quality of actual Antigravity, Meet, code-history and interview evidence on intended participant hosts still needs verification. Use this checklist before each real pilot; a blank or missing stream means *missing evidence*, never “the participant did not do it.” The older checkpoint exports measure a different procedure and cannot fill these gaps.

## Data handling and integrity

1. The natural watcher now copies only common source/text files, skips hidden files, names suggesting secrets/credentials, symlinks, `node_modules`, and unsupported file types. It limits each file to 2 MiB, each snapshot to 20 MiB/300 files, and a watcher to 250 snapshots. Output directories/files use restrictive permissions where the OS supports them. These safeguards reduce accidental collection; **they can also omit relevant code**. Inspect the file list in every final manifest against the visible project tree. If an important file is omitted, record the gap and adapt the approved capture procedure before recruitment.
2. Keep capture outputs outside the workspace and away from personal files. The screen recording and agent transcript can still contain names, notifications, account details, and external browsing. Use a clean study account/workspace, close notifications, and inspect before transfer. Do not put keys or real data in the synthetic projects.
3. For each stream, save filename, size, SHA-256, task ID, creation and receipt times, source version, and one of `received`, `missing`, `corrupt`, `declined`, or `not_applicable`. Preserve raw files separately from human labels and derived metrics. The portal currently requires six uploaded files per task; the researcher stores the approved Meet recording link separately. Verify that researcher access and download match each hash. A receipt alone does not prove readable video, transcript or complete code.
4. Use access-restricted storage, institution-approved retention/deletion dates, backups, and documented withdrawal handling. A stdlib archive audit verifies receipt hashes, manifest file hashes and final-rating linkage without executing the submission. Media still needs playback/readability inspection. Local evidence is stored under `research-portal/.local-evidence/`; the hosted release uses its configured private evidence directory. The researcher Evidence page can stream original files after role and task checks; synthetic hosted retrieval passed. Actual-file playback, capacity, retention and deletion still need exact-VM rehearsal before participant-owned-computer pilots.
5. Before session closure, the researcher checks that two task IDs have their expected conditions and stimulus revisions, two final hashes and ratings, both videos and transcripts, watcher health and code history, questionnaire/interview records, and an adjudication queue entry. Any absent item gets a reason; do not silently substitute another measure.

## Pilot release decision

Do **not** claim all measures are safe or collected yet. The hosted portal has passed synthetic ZIP delivery, authenticated size-limited upload, hash/manifest/rating checks and researcher retrieval. A real remote pilot on the **new** revision still needs an end-to-end test of exact IDE/video/transcript capture, researcher retrieval and playback, participant-host access, consented retention/deletion, and final-code security assessment with independent metadata-masked review. Until those pass, researcher self-rehearsal can test feasibility, but new-revision real participant collection remains a **no-go**. See the [current release gates](../../PILOT_READINESS_AUDIT_2026-10-18.md).
